# Метаданные товара

DAG id: `feature-platform.layers.silver.product_id.product_metadata`.

Airflow group tag: `recsys-features`.

Целевая таблица: `iceberg.silver.feature_platform_product_metadata`.

## Контракт

Путь сущности: `layers/silver/product_id/product_metadata/v1`.

Grain и primary key: `dt,product_id`.

Колонки:

- `dt` — `TIMESTAMP` начала локальной даты актуальности метаданных товара (`00:00:00 Asia/Tashkent`), рассчитанный из `data_interval_end`;
- `product_id` — идентификатор карточки товара;
- `category_id` — листовая категория из `product.category_id`;
- `l1_category_id` — верхняя содержательная категория, без технического корня `1`;
- `l2_category_id` — L2 либо L1, если отдельный второй уровень отсутствует;
- `l3_category_id` — L3 либо ближайшая существующая категория L2/L1;
- `l4_category_id` — L4 либо ближайшая существующая категория L3/L2/L1;
- `l5_category_id` — L5 либо ближайшая существующая категория L4/L3/L2/L1;
- `l6_category_id` — шестой содержательный уровень от корня; для более короткого пути содержит последнюю существующую категорию;
- `brand_id` — минимальный содержательный бренд товара после исключения технического значения `160078`;
- `shop_id` — магазин-владелец карточки товара;
- `created_at` — время создания карточки товара в UTC;
- `category_gender` — нормализованный gender листовой категории: `M`, `F`, `U` или `NULL`.

Идентификаторы хранятся как signed 32-bit `INT`. Допустимый диапазон — от `-2 147 483 648` до `2 147 483 647`; для положительных идентификаторов максимальное значение равно `2 147 483 647`. В Spark включен ANSI-режим, поэтому выход значения за этот диапазон завершает расчет ошибкой, а не приводит к незаметному переполнению.

`age_in_days` и отдельные gender-флаги в Silver не хранятся. Они вычисляются в Gold относительно его `calculated_at`.

## Источники и логика

Источники:

- `iceberg.silver.product` — базовый список товаров, листовая категория, магазин и время создания;
- `iceberg.silver_apidb_kazanexpress.public_category` — актуальная связь `id -> parent_id` для категорий;
- `iceberg.silver.sku` — связь товара с `brand_name_id`;
- `iceberg.silver.recsys_category_genders` — доминирующий gender листовой категории.

SQL явно обходит до восьми содержательных узлов категорийного пути от листа к корню. Технический корень `category_id = 1`, `NULL` и неположительные идентификаторы не считаются содержательными уровнями. В S1 публикуются первые шесть уровней от корня как L1–L6. Если путь короче шести уровней, оставшиеся колонки заполняются последней существующей категорией. Если путь глубже шести уровней, уровни после L6 не публикуются, а исходная листовая категория независимо сохраняется в `category_id`.

Например, путь `10016 → 15835 → 10596 → 16092 → 16094 → 2779 → 2785 → 18` сохраняется как `L1=10016`, `L2=15835`, `L3=10596`, `L4=16092`, `L5=16094`, `L6=2779`, `category_id=18`.

Значение `technical_category_root_id = 1` подтверждено по `public_category`: это строка «Все категории». Строка `id = 0` существует как отдельная неактивная категория, но не является корнем; связей с `parent_id = 0` и товарных категорийных путей через `0` нет.

Перед основным расчетом job проверяет, что полный путь помещается в поддерживаемый обход из восьми содержательных категорий и что каждый товар с ненулевым `product_id` ссылается на существующую положительную нетехническую листовую категорию. Глубина больше L6 сама по себе не является ошибкой.

`brand_name_id = 160078` и `NULL` исключаются до агрегации. Если у товара осталось несколько содержательных брендов, выбирается `MIN(brand_name_id)`, чтобы результат был детерминированным. Если содержательного бренда нет, `brand_id` остается `NULL`.

`category_gender` присоединяется по `product.category_id = recsys_category_genders.category_id`. Только значения `M`, `F` и `U` сохраняются; пустые и остальные значения преобразуются в `NULL`.

## Хранение и запись

Iceberg-таблица партиционирована по `months(dt)`. Дневной расчет не использует динамический overwrite месячной партиции: это удалило бы остальные дни того же месяца. Вместо этого `MERGE` полностью синхронизирует только строки текущего `dt`: обновляет существующие товары, добавляет новые и удаляет товары, которых больше нет в рассчитанном состоянии этой даты.

`NULL` не заменяется техническими нулями. В выходной схеме нет SKU и SKU-group.

## Оркестрация и DQ

DAG запускается ежедневно в `19:00 UTC`, что соответствует `00:00 Asia/Tashkent`. Стартовая дата — `2026-08-07T19:00:00Z`, `catchup=true`; при включении 22 августа 2026 года рассчитываются 14 локальных дат `dt` с 9 по 22 августа.

`dt` равен началу локальной даты `data_interval_end` в `Asia/Tashkent`. Например, `data_interval_end = 2026-08-04 19:00:00 UTC` записывает `dt = 2026-08-05 00:00:00`.

После записи DAG параллельно запускает внутренние задачи `dq` и `feature_stats`. DQ блокирует downstream при NULL или дублях в ключе `dt,product_id`; freshness, минимальный объём и изменение объёма во время первичной раскатки имеют severity `warn`. Producer дополнительно проверяет поддерживаемую глубину обхода категорий, обязательную листовую категорию и переполнение `INT`. Допустимые gender-значения и исключение технического бренда обеспечиваются самой трансформацией.

`feature_stats` запускается для той же локальной даты `dt`. Идентификаторы категорий, бренда и магазина исключены как технические ID; после исключения ключей в S1 не остаётся числовых feature-колонок, поэтому задача не выполняет полный скан данных и не записывает профили распределений.

Подтвержденные upstream DQ DAG ids для внешних таблиц неизвестны, поэтому отдельные sensors не добавлены. После merge необходимо проверить автоматически созданный PR для Iceberg maintenance.

`table.meta.create_dbt_pr: false`: собственный DQ выполняется внутри DAG, поэтому CI не создаёт для S1 новый DQ-PR в `dbt-trino`. `create_maintenance_pr: true` сохраняется.

Пайплайн использует общий Spark image с `git-sync` и минимальный общий resource profile `small`. Ресурсы следует увеличивать только по результатам наблюдения за длительностью, spill, OOM и загрузкой executors после запуска в master.

Ranking upload не настроен: таблица является внутренним переиспользуемым Silver-контрактом.
