# Silver: дневные цены SKU по динамическому ценообразованию

Дневной агрегат цен на уровне SKU по данным динамического ценообразования.
Одна строка = один `(date, sku_id)`.

## Выход и оркестрация

- Таблица: `iceberg.silver.feature_platform_sku_daily_dynamic_prices`.
- DAG: `feature-platform.layers.silver.sku_id.sku_daily_dynamic_prices`
  (`layers/silver/sku_id/sku_daily_dynamic_prices/v1/dag.py`).
- Групповой тег Airflow: `sku-dynamic-prices`.
- Расписание: ежедневно в 01:00 UTC, `0 1 * * *`.
- `start_date=2026-02-01T00:00:00Z`, `catchup=False`.

## Грейн и первичный ключ

- Грейн: `(date, sku_id)`. Группа первичного ключа — `sku_id`.
- `date` — закрытые UTC-сутки, равные `data_interval_end - 1 day`.

## Источник

- `pricing.dynamic_discount` (ClickHouse) — расчеты динамической скидки, ~7 батчей в сутки
  на каждое плечо. Внешняя upstream-таблица, репозиторием не управляется.

Витрина содержит **только дино-скидки**. Скидки по карте живут в отдельных плечах
Trino-источника `promotions.public.dynamic_discount` (`card_pricing_cb_v2_*`,
`cb_v2_sku_card_*`) и в расчет здесь не входят.

## Логика

- окно: `created_at >= date 00:00:00 UTC` и `created_at < date + 1 day 00:00:00 UTC`;
- итоговая цена наблюдения: `calculated_for_price - discount_amount`;
- агрегация идет по **всем** `promotion_id` за сутки;
- `dp_sell_price` — самая частая итоговая цена, `seller_price` — самая частая
  `calculated_for_price`;
- мода считается точно: сначала счетчики по цене, затем `argMax` по паре
  (частота, последний батч). Тай-брейк по последнему батчу нужен потому, что у ~0.8% SKU
  две цены встречаются одинаково часто;
- `prices` — уникальные итоговые цены за сутки, отсортированы по возрастанию;
- `observations` — число наблюдений «плечо x батч», из которых посчитаны моды;
- запись идемпотентна: партиция `date` перезаписывается целиком через PyIceberg `overwrite`.

### Как читать dp_sell_price

Плечи в источнике — это A/B-варианты дино-модели (`..._budget_34`,
`..._budget_34_with_cb_v2_sku_card_0526`, `unauthorized`), и каждый SKU присутствует
минимум в двух. Мода дает плечам равный вес независимо от того, сколько трафика реально
попало в каждое. Поэтому `dp_sell_price` — это самая частая цена **модели**, а не цена,
которую чаще всего видели пользователи.

Сверять `dp_sell_price` с `sell_price` из кликстрима некорректно: в кликстриме дино-скидки
и карточные скидки смешаны в одном поле.

### Почему мода, а не медиана

Цена внутри дня почти всегда стабильна: у ~70% SKU за сутки ровно одна уникальная итоговая
цена, у ~21% — две. Медиана на таком распределении вернула бы полусумму двух цен, которой
в реальности не существовало; мода возвращает фактически действовавшую цену.
`seller_price` тоже берется модой, потому что у ~3% SKU цена продавца меняется внутри дня.

## Колонки

| колонка | тип | смысл |
|---|---|---|
| `date` | DATE | закрытые UTC-сутки, партиция |
| `sku_id` | BIGINT | id SKU |
| `seller_price` | BIGINT | самая частая цена продавца за сутки |
| `dp_sell_price` | BIGINT | самая частая итоговая цена за сутки |
| `prices` | ARRAY&lt;BIGINT&gt; | уникальные итоговые цены за сутки |
| `observations` | INT | число наблюдений «плечо x батч» |

## Рантайм

ClickHouse-source пайплайн (Airflow/Python + `pyiceberg`), не Spark. Чтение — через connection
`clickhouse_sku_daily_dynamic_prices_dag`, запись — через entity-local `job/runtime.py`.
Образ задачи: `ghcr.io/daymarket/airflow:3.1.8-python3.11-ml-2`.

## DQ

Сенсора на DQ-DAG нет: источник внешний и не управляется этим репозиторием, репозиторной
DQ-DAG у него не существует. Перед записью job проверяет, что источник вернул непустой
результат, и не затирает партицию пустотой.

## Оговорки

- Серверная таймзона ClickHouse — `Asia/Tashkent`, а `created_at` имеет тип `DateTime('UTC')`.
  Границы окна задаются как `toDateTime(..., 'UTC')`; без явной зоны сутки уезжают на 5 часов.
- В источнике присутствует SKU-заглушка `sku_id = 9721786` с ценой 999 999 000 во всех батчах.
  На моду она не влияет, но агрегаты по абсолютным суммам поверх этой таблицы ее заденут.
- История источника начинается с 2026-02-01; данные старше 7 дней переезжают на
  `object_storage` и остаются доступны, но читаются медленнее.
