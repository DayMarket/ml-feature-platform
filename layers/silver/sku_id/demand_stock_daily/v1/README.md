# Silver дневного наличия SKU

Выход: `iceberg.silver.feature_platform_demand_stock_daily`.
Путь: `layers/silver/sku_id/demand_stock_daily/v1`.
Грейн и ключ: `(date, sku_id)`, identity partition по `date`.
DAG: `feature-platform.layers.silver.sku_id.demand_stock_daily`.
Группа DAG: `demand-forecast`.

## Источник и семантика

Источник — `marts.daily_sku_quantity_eod` через Airflow connection
`clickhouse_dwh_team_logistics`. Читается `FINAL`; `dt` сохраняется без сдвига.
Строка записывается только при `quantity_active_eod > 0 OR quantity_fbs_eod > 0`.
Поэтому таблица хранит множество доступных SKU, а не уровни запасов:

- наличие строки `(date, sku_id)` означает положительный доступный EOD-остаток;
- отсутствие строки означает ноль только внутри полностью записанной и прошедшей DQ
  дневной партиции;
- отсутствующая либо не прошедшая DQ партиция означает unknown, а не OOS;
- цены, seller, статусы, габариты и остальные поля исходного EOD не входят в контракт.

Технические поля `source_manifest_id`, `source_contract_version` и `ingested_at`
нужны для точного resume/read-back и не являются модельными признаками.

## Запись и проверки

До чтения строк отдельный source audit проверяет непустое выбранное множество,
уникальность ключей, допустимость ID и active/FBS значений, а также фиксирует hash
ключей и максимальный `updated_at`. Та же сигнатура повторяется непосредственно перед
commit. ClickHouse отдаёт порции размером `runtime.max_batch_rows`; `chunk_size=1`
не используется. Каждая порция проверяется по Arrow-схеме, границам ключей и лимиту
байтов.

Writer атомарно заменяет один день, сохраняет proof в metadata того же Iceberg commit
и выполняет полный read-back по контрольным суммам. При сбое старый день остаётся
целиком; retry может продолжить диапазон по подтверждённым дневным receipts. Runtime
не создаёт таблицу: migration должна быть применена заранее.

DQ выполняется после записи для каждой даты диапазона и проверяет базовые ключи,
обязательные lineage-поля и положительный `sku_id`. Штатный `feature_stats` также
запускается, но бизнес-числовых признаков кроме ключа в этой таблице нет.

## Оркестрация

Один owner DAG работает ежедневно в `04:00 UTC`, `max_active_runs=1`.
Scheduled run перестраивает последние 31 завершённый день. Тот же DAG принимает
ручной полуоткрытый диапазон, например:

```json
{"mode":"manual","start":"2026-08-01","end":"2026-09-01"}
```

Дни обрабатываются последовательно отдельными атомарными Iceberg commit. Старые
пропуски за пределами regular-окна не добавляются автоматически.

Ручной запуск без `start/end` использует
`[max(2022-09-01, UTC date(logical_date) - 31 дней), UTC date(logical_date))`.
В UI/API задайте logical date явно (например, `2026-09-01T00:00:00Z`).
Обе явные границы имеют приоритет; только одна граница — ошибка. Для manual
`mode` по умолчанию равен `manual`; бюджет такого запуска остаётся ручным.
Старт на 01.10.2022, затем первые числа месяцев и сегодняшняя UTC-дата дают
полное покрытие завершённых дней с допустимыми перекрытиями.

DQ проверяет все даты; штатные freshness и growth дополнительно работают для
вчерашнего дня относительно времени его записи. Growth использует штатный порог
20% в обе стороны и требует предыдущую партицию. `feature_stats` остаётся отдельной
параллельной задачей и сканирует каждую дату диапазона в Trino.
