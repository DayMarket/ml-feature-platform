# iceberg.gold.feature_platform_sku_buyout_features

Витрина экономики корзины и выкупаемости на грейне `sku_id`: одна строка на каждый
sku из полного sku-универса `"dwh-iceberg".silver.sku`, а не только на sku с историей
доставок. В строке — тип продавца (`1p`/`3p`), комиссия, себестоимость 1p-приёмки,
пятиуровневая категория и семь сглаженных признаков выкупаемости из
`feature_platform_buyout_online_sku_features`.

## Выход

- Таблица: `iceberg.gold.feature_platform_sku_buyout_features`.
- Ключ: `date, sku_id`.

## Оркестрация

- DAG id: `feature-platform.layers.gold.sku_id.sku_buyout_features`
  (`layers/gold/sku_id/sku_buyout_features/v1/dag.py`).
- Групповой тег Airflow: `dag.group_tag = buyout-features`.
- Расписание: ежедневно в 07:00 UTC, `0 7 * * *`.
- `start_date=2026-08-20T00:00:00Z`, `catchup=False`, `max_active_runs=1`.
- `ExternalTaskSensor` на таску `dq` DAG'а-источника
  `feature-platform.layers.gold.sku_id.buyout_online_sku_features`
  (`external_task_id="dq"`, `mode="reschedule"`, `check_existence=True`, таймаут 3 часа).
  `execution_delta = 1 час` — разница расписаний (07:00 против 06:00):
  `D 07:00 - 1ч = D 06:00`, логическая дата запуска источника, который пишет партицию `D`.

## Источники и роли

- `"dwh-iceberg".silver.sku` — база строк: весь sku-универс (10 485 803 sku на момент
  измерения, `id` уникален, у каждой строки есть `seller_id`), а также карточка, продавец,
  категория и габариты.
- `kazanexpress.public.sku` (через `trino_bx_analytics`, OLTP) — комиссия 3p (`commission`
  никогда не `NULL`, 10 486 376 строк, `id` уникален). Читается диапазонными срезами по `id`.
- `"dwh-clickhouse".marts.stock_flow_1p` — приёмки 1p-склада; из них берётся последняя
  `ACCEPTANCE` с `value_per_piece > 0` для sku 1p-продавца — источник типа `1p` и
  себестоимости.
- `"dwh-clickhouse".dict.seller` — флаг `is_1p`, чтобы отличить «принято на 1p-складе»
  от «это 1p-товар».
- `"dwh-clickhouse".dict.category` — пятиуровневое дерево категорий.
- `iceberg.gold.feature_platform_buyout_online_sku_features` (через Trino как
  `"dwh-iceberg".gold...`) — источник шести признаков выкупаемости, партиция той же даты.

## Правило 1p / 3p: антиджойн, а не UNION

Тип продавца решается антиджойном к последней 1p-приёмке, а не объединением двух
самостоятельных веток. Ветка 3p не фильтрует продавца и с самого начала содержит
все sku, которые попадут в ветку 1p, — обычный `UNION` задвоил бы ровно эти строки.
Проверено на проде:

- sku, принадлежащих 1p-продавцам (`dict.seller.is_1p = 1`): 214 060;
- ветка 1p (последняя `ACCEPTANCE` с `value_per_piece > 0` у 1p-продавца): 179 081 sku,
  и все 179 081 присутствуют в неотфильтрованной ветке 3p — это и есть множество,
  которое `UNION` продублировал бы;
- 34 979 sku принадлежат 1p-продавцам, но не имеют себестоимости
  (214 060 − 179 081 = 34 979); по согласованному правилу они уезжают в `'3p'`
  с комиссией, а не остаются без типа;
- 25 256 sku имеют приёмку на 1p-складе, но принадлежат 3p-продавцу; фильтр
  `is_1p = 1` их исключает из ветки 1p — «принято на 1p-складе» и «является 1p-товаром»
  разные вещи, приёмка на складе не делает сторонний товар первой стороной.

`commission` заполняется только для `'3p'` (`CASE WHEN one_p.sku_id IS NULL THEN
comm.commission END`), `cost_price` — только для `'1p'`.

В Iceberg `commission` хранится как `DECIMAL(19,2)`: масштаб исходной комиссии
остаётся ровно двумя знаками, а расширенная precision нужна для совместимости
PyArrow/PyIceberg при записи Parquet. Миграция расширяет существующий
`DECIMAL(5,2)` идемпотентно.

## Каскад категорий

Справочник `"dwh-clickhouse".dict.category` (6 913 категорий) хранит вместо `NULL`
нули, и обрыв уровня всегда сплошной: пары вида «l3 = 0 при l4 ≠ 0» не встречаются.
Join `silver.sku.category_id = dict.category.id` покрывает 100% строк, но нулевые
значения по уровням не редкость: l1 — 0, l2 — 23, l3 — 255, l4 — 2 077, l5 — 5 645
категорий. Поэтому у каждого уровня, начиная с l2, — каскад `COALESCE(NULLIF(...,
0), ...)` вниз по уровням до l1 включительно; l1 нулей не имеет и служит гарантированным
дном каскада.

## Почему `_shrunk`-колонки и почему `COALESCE` не нужен

Признаки `sku_buyout`, `product_buyout`, `shop_buyout` берутся из колонок
`*_buyout_rate_shrunk_90d` источника, а не из сырых `*_buyout_rate_90d`. `_shrunk`-
колонки уже посчитаны источником со сглаживанием к родителю (категории/маркетплейсу):
подстановка для sku и карточек без доставок за 90 дней в них уже встроена. Оборачивать
их дополнительным `COALESCE(sku_buyout_rate_shrunk_90d, category_buyout_rate_90d, ...)`
здесь не нужно и вредно — это было бы вторым сглаживанием поверх уже сглаженного
значения, то есть двойной подстановкой родителя вместо одной. `category_buyout` и
`category_no_show` берутся из `category_buyout_rate_90d` / `category_no_show_rate_90d`
как есть — у категории `_shrunk`-варианта в источнике нет.

## Скоуп строк и NULL-семантика

База строк — весь sku-универс (`silver.sku`), а не только sku с сигналом выкупаемости.
`feature_platform_buyout_online_sku_features` на 2026-09-09 содержит 2 889 958 строк,
ровно одну на `sku_id`. Это меньше, чем полный универс, поэтому у порядка 7,6 млн sku
(10 485 803 − 2 889 958) все семь признаков выкупаемости (`sku_buyout`,
`product_buyout`, `category_buyout`, `shop_buyout`, `category_no_show`,
`sku_n_delivered`, `product_n_delivered`) в строке — `NULL`. Это легитимное состояние
(нет истории доставок за 90 дней или sku не попал в снимок источника), а не ошибка
джойна: `NULL` здесь нельзя заменять нулём — ноль означал бы «выкупается с
вероятностью 0% / доставок 0», что для sku без истории неверно и исказит потребителя
признака.

`predicted_dimensional_group` при отсутствующих габаритах (`total_size IS NULL`)
подставляет `silver.sku.dimensional_group` как есть, но через `NULLIF(dimensional_group,
'')`: у 5 353 из 10 492 211 sku (замер на проде) справочник хранит `''`, а не `NULL`.
`COPY ... FORMAT csv` при выгрузке в PostgreSQL читает незаквоченное пустое поле как
`NULL`, поэтому без `NULLIF` Iceberg-витрина держала бы `''`, а `mlgrowth.sku_buyout_features`
— `NULL` для тех же строк. `NULLIF` убирает это расхождение на источнике: неизвестная
размерная группа — всегда `NULL`, никогда пустая строка, в обеих витринах.

## Диапазонное шардирование, а не остаток от деления

`config.yaml` задаёт `source.shards: 8`; перед циклом DAG запрашивает `min(id)`/
`max(id)` по `silver.sku` (`source_id_bounds`) и строит 8 непересекающихся
полуинтервалов `[lower, upper)` (`shard_bounds`), покрывающих всю числовую ось —
у первого среза нет нижней границы, у последнего нет верхней, чтобы sku, заведённый
между расчётом границ и чтением, не потерялся. И диапазонный предикат (`id >= lower
AND id < upper`), и остаток от деления (`id % n = k`) пушдаунятся в Postgres-коннектор
для `kazanexpress.public.sku`, но `id % n = k` не может воспользоваться индексом по
первичному ключу и вызывает полный последовательный скан OLTP на каждом срезе —
восемь модульных срезов означали бы восемь полных сканов таблицы. Диапазон — это
index range scan, поэтому восемь срезов читают OLTP суммарно один раз.
Наблюдённый диапазон на проде: `id` от 8 до 12 281 576, 8 срезов, ширина среза
1 535 197. Первый шард — это перезапись партиции (`overwrite`), остальные семь —
`append`; повтор задачи начинается заново с первого среза, поэтому запись идемпотентна.

Контрольная проверка на срезе `[1000000, 1010000)`: 8 879 строк, 8 879 различных
`sku_id`, 940 `'1p'` / 7 939 `'3p'`, ноль нарушений четырёх экономических инвариантов
(тип/комиссия/себестоимость согласованы), ноль нулевых или `NULL` уровней категории.

## Контракт чтения потребителем

`WHERE date = (SELECT max(date) FROM iceberg.gold.feature_platform_sku_buyout_features)`
— партиция полная и перезаписывается целиком, поэтому потребителю достаточно смотреть
на последнюю дату без дополнительной фильтрации по готовности.

## Выгрузка в PostgreSQL

Витрина не публикуется в `mlgrowth` этим DAG'ом. Отдельный upload DAG
`feature-platform.upload.buyout_sku_postgres_upload`
(`upload/buyout_sku_postgres_upload/v1`) выгружает её в `mlgrowth.sku_buyout_features`. `category_id` присутствует в Iceberg
(как ключ джойна с `dict.category` и для отладки), но **не** входит в состав
PostgreSQL-таблицы `mlgrowth.sku_buyout_features` — потребителю в Postgres category_id
не нужен, вниз идут только пять уровней категории (`l1_category` … `l5_category`).
